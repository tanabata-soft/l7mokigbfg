# 新しいアルバムの作り方（量産手順）

デジタルCDアルバムは「エンジン（仕組み）」と「データ（作品）」を分けてある。新しいアルバム（NK-002、NK-003…）は、エンジンに触らず、データの差し替えだけで作る。

**エンジンの正本はこのテンプレート repo（`mmishina-art/digitalcd-engine`、非公開）である。新作はこの repo をコピーして作る。** 以下の手順は、特に断らない限りコピー先の作品 repo での作業を指す。

この文書は2部構成。**前半「素材の用意」**で、Google Drive のフォルダ（曲ファイル一式）から `src/album/` に流し込める形の素材を作る。**後半「エンジンとデータの境目」「手順」**で、リポジトリへ流し込んで公開する。

シングル形態（デジタルシングルCD：最大3曲。表題曲＋カップリング＋任意のボーナストラック）の仕様は `docs/SINGLE.md` に置く。制作の流れはこの文書をそのまま縮小適用する。

## 素材の用意（Google Drive のフォルダから）

1アルバム分の曲ファイルが入ったフォルダを、そのアルバムの入力とみなす。入力形式は問わない（次項）。

**大原則: 足りないものがあっても止まらず、あるもので作り切る。** 欠けた素材は、その場で用意できる最善の代用品で**仮置き**し、アルバムとして完成させる。仮置きした箇所は「仮置きリスト」に残し、完成物と一緒に提示する（差し替えや確定は、後からそのリストに対して行えばよい）。オーナーの確認ポイントは3か所ある（①ストーリーと曲順、②ジャケット候補、③歌詞の漢字の最終確認）が、どれも進行を止める関門ではない。確認が取れない場合は推奨案を採用して進め、仮置きリストに載せる。

0. **入力検証**: フォルダ内のメディアファイルを列挙する。形式は mp4 に限らない（mp3 / wav / flac / m4a などの音声ファイル、mov / webm などの動画ファイルも可）。ffprobe で再生時間と、音声・字幕ストリームの有無を確かめる。再生用の音源は、動画なら音声トラックを取り出して用意する。動画ファイルがあれば、各曲の代表フレームを曲画像の候補として抽出しておく。フォルダ内に歌詞テキスト・画像・メモなどの付属ファイルがあれば、それも素材として取り込む（既にある歌詞やジャケット絵は、作り直さずそのまま使う）。判別できないファイルは対象外として進め、仮置きリストに残す。
1. **歌詞の読み取り**: 歌詞データ（sync.ts）の元を、次の優先順で用意する。(1) ファイルに字幕があれば抽出する。(2) 曲名（と歌手名）が分かれば、ネットで歌詞や公式情報を調べて補完・照合に使う。(3) どちらも無ければ、文字起こしで仮の歌詞を作る。字幕がローマ字のみの曲は日本語表記に変換する。漢字の当て方で迷う箇所は断定せず「要確認」として仮置きリストに残す。字幕以外の経路で得た歌詞には行ごとの開始時刻が無いので、文字起こしのセグメントと照合して時刻を付ける（NK-001 のハイライト補正と同じ方法）。どの経路でも、最終の読みの確定は耳の仕事（仮のまま完成させてよい）。
2. **メタデータの整え**: 表示タイトルを決める（ファイル名のままにしない。正式な表記に整える）、ジャンルを付ける、再生時間を実測で確定する。曲名が分かれば、ネットの情報（ジャンル、歌手、発表時の情報など）でも補完する。出典のはっきりしない情報は仮置きリストに載せる。歌詞データのキー（tracks.ts の `src`）もここで決める。
3. **ストーリーと曲順【確認ポイント①】**: 全曲の歌詞から、アルバム全体の物語（コンセプト）を組み立て、それに沿って曲順を決める。ジャンルの流れと再生時間のバランスも見る。確認が取れればそれを正とし、取れない場合は推奨のストーリーと曲順で進めて仮置きリストに載せる（ここが後で変わると文章もジャケットも手戻りになるので、リストの中では最優先で確定してもらう）。
4. **ブックレット文章**: ライナーノーツ（見出し2つ）と、曲ごとの解説（歌詞とストーリーに沿って書く）、奥付を用意する。カタログ番号は NK-002 以降の連番を付番する。
5. **曲画像**: フォルダ内に曲の画像が既にあれば、それを優先して使う。映像のある曲は 0 で抽出したフレームを基本にする（`trackNN.jpg`）。音声のみの入力や、映像のない・使えない曲は、歌のイメージに合わせて生成する（音声ファイルだけのアルバムでは、生成が既定の経路になる）。
6. **ジャケット一式**: 表ジャケットと背景は、アルバム全体のイメージで複数候補を作り、オーナーが選ぶ【確認ポイント②】。選択が無い場合は推奨候補を採用し、仮置きリストに載せる。裏ジャケットは曲画像のモザイクで自動生成する。アプリアイコンは表ジャケットから作る（`scripts/make-icons.mjs` のコメントの手順）。表ジャケットの様式は `docs/ALBUM-DESIGN-STUDY.md` の型（型A〜J）から作品の性格に合わせて1つ選び、タイトル配置・書体・色彩・帯の扱いなどのパラメータを型の定義で決める。
7. **時刻の検証と歌詞の確定**: 歌詞の開始時刻が実際の歌い出しと合っているかをサンプル照合で確かめる。等間隔の人工的な時刻が付いている素材はずれている前提で、文字起こしとの照合で補正する（NK-001 で実際に必要だった）。漢字の「要確認」はオーナーの耳で確定する【確認ポイント③】。確定しなくてもアルバムは完成として扱い、未確定分は仮置きリストに残す。

そろった素材は、次の「エンジンとデータの境目」の形に置く。**納品・公開の報告には、仮置きリスト（仮置きした箇所と、その理由・代用品の内容）を必ず添える。**

### 素材まわりの実務メモ

- **受け取りの現行形**: 曲の生成はオーナーが自分の Gemini アプリ（AI Pro）で行い、チャットへ MP4 をアップロードするのが標準の受け取り方。Google Drive フォルダ経由で渡された場合も、以降の手順は同じ。
- **動画末尾の処理**: Gemini 生成の動画は、末尾にロゴのアウトロ映像が付くことがある。音声側の音楽終了点（フェードアウトの終わり）を実測してそこで切り、末尾の無音も詰める。表示上の尺はプレイヤーの表示に合わせて確定する（NK-S004 で実施）。
- **歌詞の時刻付けの検証**: 字幕の表示時刻は信用しきらない。付けた開始時刻は、単語レベルの文字起こし（faster-whisper small、VAD なし）で照合し、確定前に別モデル（medium）のフレーズ境界時刻と突き合わせる（片方だけでは全体のずれを見逃す。NK-S003 では約7〜12秒のずれが実際にあった）。字幕のウィンドウが後半で実歌より遅れることや、字幕が抜ける区間があること（その区間も歌は続いている）がある。抜けた行は文字起こしから補い、補った行とその時刻は仮置きリストに明記する。
- **インスト曲の扱い**: 歌詞のない曲は `sync.ts` に空配列を入れて成立する。その場合は、歌詞前提の内容チェック（`scripts/content-checks.mjs`）と単体テストの歌詞長の前提を、インスト契約に合わせて調整する（実施例は NK-S004 のリポジトリ）。
- **単体プレビューの音源キャッシュ**: `npm run build:preview` はプレビュー用に音源を再エンコードし、`node_modules/.cache` にキャッシュする。新作では build:preview の前にこのキャッシュを消す。前作の同名ファイルが残っていると、前作の音源が埋め込まれる事故が実際に起きた。プレビューを渡す前に、埋め込まれた音源の長さを実測して確かめる。

## エンジンとデータの境目

- **エンジン（作品ごとに触らない）**: `src/` のうち `src/album/` 以外（main.ts / logic.ts / style.css / pwa.ts / install.ts / debug.ts）、`index.html`、`public/boot.js`、`scripts/`、`vite.config.ts` の仕組み部分。
- **データ（作品ごとに差し替える）**: `src/album/` の中身ぜんぶ。
  - `album.ts`: 題名、カタログ番号、ライナーノーツ（本文と見出し）、奥付の文面。
  - `tracks.ts`: 曲目（題名・ジャンル・再生時間・解説、`src` は歌詞データのキー）。並びが曲順。
  - `sync.ts`: 歌詞の同期データ（生成物）。形は `{ "曲のsrc": [[開始秒, "歌詞"], ...] }`、キーは `tracks.ts` の `src` と一致させる。時刻は単調増加。
  - `media.ts`: 曲ごとの画像・音源の対応表。曲数分の import を並べ、`TRACK_IMG` / `TRACK_AUDIO` を曲順に export する。
  - `assets/img/`: 固定の置き場所（スロット）が決まっている。
    - `jacket.jpg`（表ジャケット）、`back.jpg`（裏ジャケット）、`bg.jpg`（背景）
    - `track01.jpg` 〜 `trackNN.jpg`（曲ごとの絵。NN は2桁ゼロ埋め、曲数分）
  - `assets/audio/`: `track01.mp4` 〜 `trackNN.mp4`（曲順）

## 手順

1. **リポジトリを用意する。** テンプレート repo（`mmishina-art/digitalcd-engine`）をコピーして、新しいリポジトリを作る（GitHub で新規作成し、中身を移す）。**置き場所は配布用 Organization `tanabata-soft` の下、名前は作品名を含まないランダムな文字列にする**（URLから作品や持ち主が分からないようにするため。オーナー指示 2026-11-04）。作品とリポジトリ名・URLの対応は各リポジトリの `docs/HANDOVER.md` に残す。
2. **アプリ ID と版数を変える。** `package.json` の `name` を新しい ID に（例: `kiso-album-2`。**既存のアルバムと別の名前にすること**。同じ `tanabata-soft.github.io` に載るため、同じ ID だと保存データや Service Worker のキャッシュが混ざる）、`version` を `1.0.0` に戻す。
3. **`src/album/` を差し替える。** 上の境目に沿って、album.ts / tracks.ts / sync.ts / media.ts / assets を新しい作品の内容にする。`sync.ts` は前半「素材の用意」の手順で作る（作り直しの詳細は `docs/HANDOVER.md`）。
4. **アプリ名と色を付け替える（2か所ルール）。** `vite.config.ts` の `APP_NAME` / `THEME_COLOR` / `BACKGROUND_COLOR` と、`index.html` の `<title>` / `theme-color` / `apple-mobile-web-app-title` を新しいアルバムに合わせる（`npm run check:content` が一致を確かめる）。テーマ色に合わせて `src/style.css` の `:root` の色（`--indigo` など）も変えてよい（ここはエンジン側だが、配色は作品の世界観の一部として付け替え対象とする）。
5. **アイコンを作り直す。** 新しい `jacket.jpg` から、`scripts/make-icons.mjs` のコメントの手順で `public/icons/` の4点を置き換える（`npm run icons` で寸法を確認）。
6. **画面テストの期待値を合わせる。** `e2e/app.spec.ts` の曲数・ブックレットのページ数（曲数+3）・曲タイトルなどを、新しい収録内容に直す。`scripts/shots.mjs` はテンプレートではシングル形態用（撮影対象は表・裏・再生・インストール）になっている。アルバム形態では、曲目画面とブックレット画面の撮影と、ブックレット経由のインストール入口を対象に戻す。
7. **確かめる。** `npm run verify`（lint・単体テスト・ビルド・PWA成立・内容整合）と `npm run test:e2e`、`npm run shots`（`shots/all.png` で見た目を確認）を通す。作業中の確認は `npm run build:preview` の単一 HTML で。
8. **公開する。** 新しいリポジトリの Settings → Pages → Source を **GitHub Actions** にし、`main` の保護ルール（`protect-main`: PR必須、status checks `check` と `e2e`、force push禁止）を設定する。作業は feature ブランチ → PR → CI が通ったらマージ（既定の流れ）。

## 注意

- 公開済みのアルバムは、それぞれ独立したリポジトリとアプリ ID を持つ。エンジン側の直しは公開済みの作品に自動では効かない（作品が壊れないための割り切り）。同じ直しを複数作に当てるときは、各リポジトリに同じ変更を入れる。
- **裏面の下絵（back.jpg）のなじませ（オーナー指示 2026-11-04）**: 裏面の下絵に曲ジャケットを並べるときは、ジャケットに焼き込まれた白枠・紙枠・額縁マットをそのまま使わない。枠の厚みを実測して内側の絵だけを切り出し、上下の継ぎ目にはクロスフェード（目安90px）を入れてなじませる（NK-S002 v1.1.1、NK-S003 v1.0.2 で実施）。再生画面の曲ジャケット（trackNN.jpg）自体は元のままでよい。
- Netlify は使わない（公開はすべて GitHub Pages に一本化。2026-11-10 決定）。

## 表ジャケットと裏面のルール（2026-11-05 オーナー決定、NK-001 で確立）

### 表ジャケット
- 題材はライナーノーツの世界観から決める。生成絵に文字は描き込まず、タイトルは後付けで合成する。
- タイトルの配置は、ホーム画面アイコン（角丸・円形マスク・小サイズ表示）で欠けない範囲に収める。アイコンプレビューで先に確認する。

### 裏面（曲ジャケットのモザイク。シングル裏面の「2曲結合＋クロスフェード」とは別形式のルール）
- **グリッドは曲数で判断する**：〜9曲＝3列×3段（1マス 600×600）、10〜12曲＝3列×4段（600×450）か 4列×3段（450×600）、13〜16曲＝4列×4段（450×450）。12マスの2形式は、曲絵の構図（上下を切るか左右を切るか）で選ぶ。
- **マスが余ったら、最下段側の余りマスをタイトル面が埋める**。タイトルだけは例外で、余った面積を埋めるサイズにする。
- **駒は曲の絵だけ**。曲でない絵（背景用の風景画など）は駒として入れない。ただしタイトル面の背景に使うのは可（作品の背景絵＋半透明の暗幕で文字を立てる）。
- 各曲の絵は**判型いっぱいにトリミング**して入れる。縮小して全体を見せる方式（自分の絵のぼかし背景つき）はしない。結果として**曲タイトルが切れてもよい**。
- マス同士は**隙間なくみっちり突き合わせる**。溝（ガター）もフェードも入れない。
- 曲ジャケットに焼き込まれた白枠・紙枠は、**輝度プロファイルで深さを実測して切り落とす**（例：右30px・上15px）。再生画面の曲画像は元のまま使う。
- **曲目リストは裏面に印刷として入れる**（全曲・曲順どおり・時間入り、ボーナストラックは BONUS 表記、絵のない曲もリストには載せる）。表示専用で、ここからジャンプはさせない。印刷した作品は `album.ts` の `printedBackList` を true にして、アプリ側の重ねリストと一本化する。
- 例外：絵が作品の世界観に合わない曲は、オーナー判断でコラージュから外してよい（曲目リストには載せる）。

## 運用ルール（引き継ぎ用）

このシリーズの運用ルール。制作手順とあわせて、公開・運用はこの決まりに従う。

- **コミットの author は `muse <muse@localhost>` にする。** 実際の Gmail アドレスを使うと、GitHub の email-privacy 設定で push が拒否される。
- **公開フロー**: feature ブランチ → PR → CI（check と e2e）が通ったら squash マージ → GitHub Pages の反映を確認する。main への直接 push はルールセット「protect-main」で禁止。**`[skip ci]` を付けると必須チェックが満たされずマージできなくなる**ので、文書だけの変更でも付けない。
- **版数**: `package.json` の `version` が唯一の管理場所。公開のたびに必ず上げ、納品報告に版数を明記する。
- **検証の関門（デジタルCD系列の決定、2026-11-05）**: 公開の関門はローカル検証（`npm run verify` ＋ e2e ＋ `npm run shots` の目視）を報告することと、単体HTMLプレビュー（`npm run build:preview` で作り、`~/workspace/your_files/` に置く）でのオーナーの実機確認。GitHub Actions の CI は予備の信号であり、関門そのものではない。
- **e2e の注意**: ポート 4173 に別リポジトリのプレビューサーバーが残っていると、`reuseExistingServer` でそちらに接続して大量に失敗する。実行前に 4173 の占有を確認し、埋まっていたら使っていないポートに変えた一時設定で回す（その変更はコミットしない）。
- **依存関係が壊れたとき**: まず `bash tools/install-v4.sh <repo>`（監査 bad:0 が基準。スクリプトはテンプレート repo の `tools/` に同梱、説明は `docs/TOOLS.md`）。個別のパッケージは `node tools/extract-one.cjs <pkg>@<ver> <dest>` で修復する。この作業 VM では実物が `~/workspace/.nk-test/` にあり、そちらを使っても同じ。
- **仮置き**: 素材が欠けていても止まらず、代用品で仮置きして作り切る。その場合、納品報告に必ず「仮置きリスト」を添え、何が仮置きで、確定には何が要るかを明記する。
- **ダッシュボード**: シリーズの現況は「デジタルCD ダッシュボード」（Muse のアーティファクト、slug `dezitarucd-datusiyubodo`）に集約されている。公開や確認の進展があったら、その場で台帳・かんばん・メトリクスを実態に合わせて更新する（後追いのまとめ更新はしない）。レビュー列の項目は、オーナーが確認して声をかけた時点で消し込み、全て終わったら完了列へ移す。
- **Dependabot PR は当面放置する**（オーナー決定、2026-11-06）。対象は開発用ツールの minor/patch 更新だけで、公開中のアプリに影響はない。各作品を次に変更するときに、ついでに取り込む。
- **エンジン改良の置き場所**: エンジン側の改良は、まずこのテンプレート repo（`mmishina-art/digitalcd-engine`）に入れる。公開済み作品へは自動では効かないので、必要な作品には個別に移植し、各作品の `docs/HANDOVER.md` に記録する。
