# デジタルCDシリーズ 制作の引き継ぎ

あなたは「デジタルCD」シリーズの制作を引き継ぎます。これはスマートフォン向けの音楽アプリ（PWA）を1作品ずつ作る仕事で、核にあるのは「配信（借りる）ではなく所有する」という所有感です。作品はアルバム（デジタルCDアルバム）とシングル（デジタルシングルCD）の2形態があります。

## 最初にやること

1. エンジン（テンプレート）リポジトリ `mmishina-art/digitalcd-engine`（非公開）を用意する。ローカルでは `~/workspace/digitalcd-engine/repo/`。
2. `docs/START-HERE.md` を読む。ここに全体の進め方と読む順番がある。以後は `docs/PRODUCTION.md`（手順と運用ルール）、`docs/SINGLE.md`（シングルの仕様）、`docs/TOOLS.md`（道具の用意のしかた）が正本。
3. 新作は、直近の作品のリポジトリではなく、このテンプレートをコピーして作る。

## 分担

- 曲の生成はオーナー（三品 正人さん）が自分の Gemini アプリ（AI Pro）で行い、チャットへ MP4 をアップロードして渡す。Gemini API で音楽生成はしない（API は音声合成専用という決定）。
- ジャケット原画の素材提供もオーナー側。制作側は受け取った素材から組み立てる。
- 確認ポイントは3か所（①曲の組み合わせと曲順 ②表ジャケット候補 ③歌詞の漢字の最終確認）。ただし進行を止める関門ではない。回答がなくても推奨案で進め、選んだものは「仮置き」として納品報告の仮置きリストに必ず残す。素材が欠けていても止まらず、あるもので作り切るのが原則。

## 守ること

- 公開先は GitHub の組織 tanabata-soft。リポジトリ名はランダムな文字列にし、公開する。コミットの author は `muse <muse@localhost>`。公開は「ブランチ → PR → CI → squash マージ → GitHub Pages」の順で、コミットメッセージに `[skip ci]` を付けない（必須チェックが成立せずマージできない）。
- 版数は package.json の version で一元管理し、公開のたびに上げて、納品報告にバージョン番号を明記する。
- 検証の関門は、ローカルの検証（verify・e2e・shots）を通して報告することと、単体ファイル版プレビューでオーナーが実機確認すること。GitHub の CI は予備の信号。
- 公開したら、その作品の docs/HANDOVER.md を最新に保つ。シリーズの現況の集約先はデジタルCDダッシュボードで、アクセスできない環境では各作品の HANDOVER.md が作品ごとの正本になる。
- Dependabot の PR は放置し、各作品を次に変更するときに取り込む（決まり）。

## 報告のしかた

- 報告は、最初の行に結論を短く書き、空行を挟んで詳細を書く。
- オーナーに何かしてもらう必要があるときは、報告とは別のメッセージで、作品名を明記して「お願い」として切り分ける。お願いがないときはその欄自体を出さない。
- 指示が二通りに読めるとき（特に画面・デザイン・範囲）は、着手前に意図を言い直して確認を取る。些細な一手の命令は除く。
